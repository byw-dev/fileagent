# A 基线审计（AUD）— 工作章程

> **状态**：⬜ 待执行 ｜ **立项**：2026-09-24 ｜ **执行方式**：**独立新会话**（理由见 §2）
>
> 这份文档是**一把尺子，不是一份答案**。它规定审计怎么做、做到什么程度算完，
> **刻意不包含任何关于系统现状的判断**。

---

## 1. 目的

给出一个**可信的**回答：**「距离一个可运行的版本（目标 A），我们还缺什么？」**

立项背景（事实，非判断）：2026-09-08 的审计发现「Agent 数据面从未端到端跑通过」，
**在那之前写的排期都建立在「核心链路是通的」这一已被证伪的前提上**。因此重排的前提是
——先知道现在真正有什么。

**目标 A 的定义**（2026-09-24 产品拍板）：

> 一台 agent + Control Plane + Web UI，配置一条采集规则，
> **文件能采上去、索引里能查到、能下载**。
>
> 其余一律不算 A：多 agent、MinIO↔PG 对账、标签/数据集、SDK、监控、UI 重做。

---

## 2. 为什么必须在独立新会话执行

本审计要回答「什么是现状」。如果执行者带着上一轮会话的既有结论进场，它会把那些结论
当作基线，只去审自己没断言过的部分——**而那正是本项目反复出问题的机制**。

**已有实证**：立项这次会话中，协调者（我）曾把一个错误的合并语义（`max(redis, pg)`）
写进返工 spec，来源是评审自己上一轮的建议，未独立推导即采纳，后被第三轮推翻。
**结论：不要信任任何 agent 的断言，包括写这份文档的那一个。**

---

## 3. 硬规则：本文档不含现状判断

本文件**不得**出现「X 已落地 / Y 未落地 / Z 能跑」这类状态断言。
理由：这份文档会被执行者当作基线读；写进去的任何错误断言，都会在审计开始之前污染结论。

允许写的是：**范围、方法、纪律、产出格式、验收标准**。
（§6 的校准集是唯一的例外，且它被定义为**待重新发现的对象**，不是给定结论。）

## 4. 审计对象：A 链路（以问题形式列出）

对下列每一环，回答**两个问题**：

- **(a) 它真的能跑吗？** —— 以**在 dev 环境实际执行**为准，不以测试通过为准。
- **(b) 仓库关于它的声称，与代码/行为一致吗？** —— 文档、注释、迁移说明、任务卡、卡片正文。

| # | 环节 | 要回答的问题 |
|---|------|-------------|
| ① | CP 启动 | 四个依赖（PG / Redis / MinIO / NATS）齐备与缺失时各是什么行为？启动即失败还是延后爆？ |
| ② | 管理员登录 Web UI | 能登录吗？凭据从哪来？首次初始化的路径是什么？ |
| ③ | Agent 注册 → 审批 → gRPC 连接 | 完整状态机能走通吗？每个状态的转换条件是什么？ |
| ④ | Agent 获取 STS 凭据 | 能签出吗？有效期与刷新是怎样的？失败时表现如何？ |
| ⑤ | 建 bucket | 通过 UI/API 建的 bucket，后续环节是否都认它？ |
| ⑥ | 建采集规则 | 规则的必填项、校验、失败反馈是什么？ |
| ⑦ | 规则下发到 agent | 下发链路是什么？agent 重连/规则变更时如何同步？ |
| ⑧ | agent 监听并发现文件 | 监听机制是什么？启动前已存在的文件会被采吗？ |
| ⑨ | agent 直传 MinIO | 小文件与大文件分别走什么路径？失败与续传如何？ |
| ⑩ | 上报 → CP 索引 | `file_entries` 的哪些字段会被填？失败上报如何处理？ |
| ⑪ | UI 文件列表 / 查询 | 列表、分页、筛选能用吗？ |
| ⑫ | UI 下载 | 预签名 GET 能下到正确内容吗？ |

> ⚠️ 这张表是**问题清单**。执行者不得把任一行当成「该功能存在」的背书。

## 5. 两层检查手段

### 5.1 机械层（脚本判定，必然收敛）

这一层不需要判断力，**必须先做**，因为它能穷尽且可复跑。缺陷的共同签名是
**「一句声称里点了名的、可查证之物」**：

| 声称形态 | 机械检查 |
|---|---|
| 「configurable via `X`」/ 任何环境变量名 | `X` 在代码里被读过吗 |
| 点名的函数 / 表 / 列 / 文件 / 字段 / 命令 | 它存在吗 |
| 「periodic」「每 N」「启动时」「后台」 | 有调用方 / 调度器吗 |
| 「返回 4xx / 5xx / 200」 | handler 真这么返吗 |
| 「N 项 / N 条 / 共 M 个」 | 被点名的脚本或表里真是这个数吗 |
| `t.Skip` / build tag 的环境闸门 | CI 提供那个依赖吗（**不提供 = 该测试在 CI 里从未跑过**） |
| 写明的门槛（覆盖率、性能、上限…） | 有任何东西在执行它吗 |
| 指向文件/章节的引用（`§x.y`、相对路径） | 目标存在吗 |

### 5.2 实证层

把 ①→⑫ 在 dev 环境**真跑一遍**，记录每一步的实际命令与实际输出。

**不得以「单元测试通过」替代**——本项目有过空心功能通过全部 mock 单测的先例。

## 6. 校准集（先用你的方法重新发现它们）

下列四条在 2026-09-24 被实际撞见过。**不要把它们当成给定结论，
而要当成对你方法的检验**：

```
1. WEBHOOK_MAX_PARSE_BYTES   —— 曾被文档/日志声称「可配」
2. 某条迁移的 cleanup 说明     —— 曾声称 periodic 执行
3. readBodyCapped 的注释       —— 曾声称 hash 基于完整 body
4. IC-BUG-7 卡片正文           —— 其前提曾被后续改动推翻
```

**如果你的机械层跑完没有独立捞出这四类问题（或确认它们已被修复），
说明方法太弱——先改方法，再继续。**

## 7. 纪律

1. **代码是最终真相**（CLAUDE.md 的权威顺序）。文档与代码冲突时，以代码为准，
   并把冲突记为一条发现。
2. **不信任何 agent 的断言**，包括本文件、包括你自己上一轮的结论。断言必须带证据
   （命令 + 实际输出，或代码位置）。
3. **断言「不存在 / 从不 / 只有 N 种」之前，先去找反证面。** 本项目已有多条自写的
   穷尽性断言被读码证伪。
4. **CI 绿不证明任何未运行的东西。** 检查 skip 闸门与 CI 实际提供的依赖。
5. **审计只读。** 发现问题**不要顺手修**——修是另一刀。这条是防止审计变成无界的
   修复工程（本项目一刀 4 轮评审的先例说明这个风险是真的）。
6. **不得依赖自己的中途总结**；发现物就地记录证据，不要事后凭记忆重建。

## 8. 产出

一份报告，含三部分：

**(1) 逐环判定**：① … ⑫ 每一环给 **能跑 / 不能跑 / 未验证**，附证据。

**(2) 声称漂移清单**：每条 = 声称出处（文件:行）+ 实际情况 + 证据 + 严重度。

**(3) 缺口清单**，每条打上**二分标签**：

- **挡 A** —— 不解决则目标 A 不成立
- **不挡 A** —— 记录并归档，**不在此轮处理**

> ⚠️ 现有的「挡 / 可推」判据**不能直接沿用**：它 2026-09-11 重判过一次，判的是
> 「挡着能不能扛住故障」，**不是「挡着能不能用」**。本轮必须按 A 的标尺重新分。

---

## 9. 验收标准

审计完成 = 同时满足：

- [ ] ①–⑫ 每一环都有带证据的判定，无「未验证」遗留（若确实无法验证，须说明为什么）
- [ ] 机械层的每一类检查都有可复跑的脚本或命令记录
- [ ] 校准集四类问题被独立重新发现或确认已修
- [ ] 每条缺口都打了 **挡 A / 不挡 A**
- [ ] 报告中没有任何无证据的状态断言
