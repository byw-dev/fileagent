## 0. 执行原则（必须遵守）

- [ ] **先审计再改文档**：先确认代码与测试真实状态，再更新任务状态。
- [ ] **禁止猜测完成度**：所有“已完成”必须附证据（commit / test / 文件路径）。
- [ ] **统一口径优先级**：`DECISIONS.md`（规范） > `docs/design/*`（设计） > `docs/tasks/*`（执行状态）。
- [ ] **每次改动保留“变更理由”**：避免未来再次出现“状态不清楚”。

## 1. 代码与测试状态审计（T3-5 核心）

### 1.1 字段统一映射核对（D-009）

逐项核对以下字段在 DB / proto / CP REST / Agent / WebUI 是否一致：

- [ ] `base_path`
- [ ] `path_pattern`
- [ ] `dest_path_template`
- [ ] `bucket_id`（DB/REST）
- [ ] `upload_bucket`（proto，bucket 名称）
- [ ] `recursive`
- [ ] `append_mode`
- [ ] `mode`（统一小写语义）
- [ ] `enabled` / `is_active`（桥接一致）

输出要求：
- [ ] 产出“字段映射现状表（as-is）”
- [ ] 标记每项：`一致 / 不一致 / 不确定`
- [ ] 不一致项必须附文件证据（路径+行）

---

### 1.2 高风险逻辑专项核对

- [ ] `append_mode` 默认值为空时是否为 `"overwrite"`（不得为 `"none"`）
- [ ] `mode` 大小写是否在输入/存储/展示全链路归一化
- [ ] `bucket_id -> upload_bucket` 转换是否由 CP 下发链路稳定执行
- [ ] `enabled/is_active/status` 映射是否双向一致（创建、更新、回显）

---

### 1.3 `pkg/trollsift` 及调用链核对（T3-4/T3-5 交叉）

- [ ] `Parse` 能否正确提取变量
- [ ] `Compose` 能否正确重格式化
- [ ] `Globify` 规则是否与调用方预期一致
- [ ] `IsTrollsiftPattern` 判定是否导致误判（必要时记录风险）
- [ ] Agent/CP 调用点是否均改为共享库实现（无重复分叉逻辑）

---

### 1.4 回归测试覆盖核对（特别是 WebUI）

- [ ] WebUI 规则创建测试（字段提交）
- [ ] WebUI 规则编辑测试（字段回显）
- [ ] WebUI 列表/详情展示测试（字段展示一致）
- [ ] 后端 API 测试（请求/响应字段一致）
- [ ] 端到端关键路径测试（创建规则 -> 下发 -> Agent 执行）

验收判定：
- [ ] 若任一关键测试缺失，T3-5 不得标记“已完成”。
