# 存储事件源调研（B2）：SeaweedFS filer 元数据订阅能否当 CP 的入站事件源

> 2026-10-12 · SeaweedFS 4.48（镜像 digest 同 D-037 / 存储层调研）· 本机单节点（master+volume+filer+S3 一个进程，filer 元数据库 leveldb3）
> 对应 [`DECISIONS.md`](../../DECISIONS.md) D-037 第五条的四项待查；结论已回填该条。
> 工具与结果：[`research/event-source/`](../../research/event-source/)（`eventsource watch|load|ops` + `analyze.py`，`results/` 是汇总与操作翻译样本；原始事件日志较大未入库，可重跑）。
> **数字的性质**：①源码结论按文件与函数给出；②乱序幅度、心跳间隔等是**本机**测得，硬件更慢或负载更重时会变大，只能当下界看。

## 0. 结论先行

1. **订阅用 `SubscribeLocalMetadata`，并打开 `client_supports_idle_heartbeat`。** 本地流上的空闲心跳是一个**完备性声明**：
   心跳带的 `ts_ns` 已被「尚在途中的事件里最早那条」封顶，而且发送前会复查缓冲区头部——**心跳之后不会再收到 `ts_ns` ≤ 它的事件**。
   聚合流（`SubscribeMetadata`）的心跳只是 `now`，没有封顶，不能当游标用。
2. **持久游标 = 最近一次心跳的声明值。** 不需要「回退窗口」这个经验参数；重连后从声明值续订，期间重放的事件靠 CP 的幂等写入吃掉
   （D-037 本就要求按路径回读当前状态再写索引）。代价：持续满载时心跳不发（只在订阅方追上缓冲区头部时发），游标会停在最后一次空闲时刻，重启时重放更多事件。
3. **事件流不是严格按时间戳有序，而且乱序比以前测的大得多。** 并发 128 时 8.5% 的事件晚于已收到的最大时间戳到达，最大晚 7.75ms（存储层调研测得约 0.1ms）。
   所以「≤ 游标即丢」一定会丢事件，回退窗口若要用也不能按毫秒设——这正是第 2 条用心跳声明的理由。
4. **filer 硬崩溃会无声地丢掉尚未落盘的事件，而且重启后的水位会把这段丢失「盖过去」。** 订阅方离线时写入 6386 个对象后 `kill -9`：
   对象全部还在（元数据库是持久的），事件 0 条；重启后心跳里的落盘水位直接等于当前时刻。**从事件流本身无法发现这次丢失。**
   → 对账（L2）不是可选项；另外适配器应在每次断流重连后，把「上次声明值 → 重连时刻」这段标记为待核对（正常情况下只有几秒）。
5. **事件翻译规则很简单**（见 §4 实测表）：只认 `/buckets/<桶>/` 下的**非目录**条目；新建 / 覆盖 / 删除各一条事件；
   过滤 `/buckets/.system/` 与 `/buckets/<桶>/.uploads/`；分片上传完成时只出现一条最终对象的新建事件；拷贝就是一条新建；
   删一个不存在的对象没有事件；**删桶只有一条「桶目录删除」，其下对象不再逐条发事件**（leveldb3 整库删除）。

## 1. 待查一：在途水位对外部订阅方是否成立（源码）

- `weed/filer/filer_notify.go`：每个事件先 `metaLogInflight.stamp()` 盖时间戳并登记为「在途」，追加进日志缓冲后 `done()` 注销（追加失败也注销）。
  `claimThrough(now)` 返回 `min(now, 最早在途时间戳 − 1)`，并把它记为下限：之后盖的时间戳一定大于它。
- `weed/server/filer_grpc_server_sub_meta.go` `maybeSendIdleHeartbeat`：
  - 只对请求里 `ClientSupportsIdleHeartbeat=true` 的订阅方发——**任何外部客户端都可以打开**，不限于 filer 之间；
  - 只在订阅方已经读到缓冲区头部时发（`logBuffer.LastTsNs <= 已读位置`），间隔 5s（有远端 peer 时 200ms，不可配置）；
  - **本地流**：`heartbeat.TsNs = LocalDeliveredThroughTsNs(now)`（即 `claimThrough`），同时带 `FlushedTsNs = LocalFlushedThroughTsNs(now)`；
    取完声明后再查一次缓冲区头部，头部前进了就这次不发。源码注释把这个论证写得很完整：「声明值及以下的事件，要么在途（封顶了声明），要么在声明之后盖戳（被下限挡在上面），要么已追加——那么头部复查证明本流已发出」。
  - **聚合流**：`TsNs = now`，没有在途封顶，也没有头部复查。
- 实测（§3 的三组负载，每组同时订两条流）：本地流共 55 次心跳、0 次违例；聚合流在单 filer 下也是 0 次——但那只是没撞上，代码上没有保证。

## 2. 待查二：负载下的时间戳乱序

| 负载（本机） | 事件数 | 乱序事件占比 | 晚到 p99 | 晚到最大 | 心跳次数 / 最大间隔 |
|---|---|---|---|---|---|
| 并发 32，每个写手间隔 100ms（约 300 次/秒，持续 150s） | 44,701 | 1.0% | 0.89ms | 2.03ms | 32 / 5.1s |
| 并发 16，5s 突发 + 7s 空闲 ×4（约 6,500 次/秒） | 130,156 | 2.5% | 0.90ms | 2.38ms | 11 / 5.2s |
| 并发 128，同上 | 163,577 | 8.5% | 3.49ms | 7.75ms | 12 / 5.2s |

- 乱序上界 = 盖戳到追加之间的耗时，随并发与负载增长；以上是本机下界。
- 三组都是**全部写入都有对应事件**（`writes_missing_events = 0`）。
- 突发期间不发心跳（订阅方一直落后于头部），最大间隔约等于突发长度；轻负载持续写入时心跳照常每 5s 一次。

## 3. 待查三：崩溃窗口与游标越界

- **硬崩溃**（订阅方离线，3s 写入 6,386 个对象，2s 后 `docker kill -s KILL`，重启后从写入前续订）：事件 0 条，对象 6,386 个都在（`fs.du`）。
  重启后第一次心跳的 `flushed_ns` 就等于当时的时间——丢失段被新进程的水位覆盖。这与存储层调研的 e2c（0/200）一致，且补上了「水位不会暴露丢失」这一点。
- **落盘水位**：本地流心跳的 `flushed_ns` 呈 0–60s 锯齿（元数据日志每分钟落盘一次，`LogFlushInterval`）。它说明「多旧的事件已经安全」，但如上所述，崩溃后它不可信。
- **filer 签名不能用来发现重启**：`Filer.Signature` 存在元数据库里（`setOrLoadFilerStoreSignature`），重启不变；它只在**换了元数据库**时变化——这倒可以用来发现「库被换掉」（D-037 部署补充里那个「改 `filer.toml` 换库，旧数据消失」）。
- **游标越界自检**：元数据日志布局是 `/topics/.system/log/<YYYY-MM-DD>/<HH-MM>.<filer 签名>`，每分钟一个文件。适配器启动时经 filer 列出最早一天、最早一个文件，若游标早于它，说明那段已被 `fs.log.purge` 清掉——订阅会静默跳过（存储层调研 `results/subscribe/purge/` 已实测），必须告警并触发对账。

## 4. 待查四：事件翻译（实测，`results/ops*.jsonl`）

| S3 操作 | 事件（`dir` / 旧条目 → 新条目） | 适配器怎么处理 |
|---|---|---|
| 建桶 | 新建 `/buckets/<桶>`（目录）；另有 `/buckets/.system/owners/...` 的新建与更新 | 忽略目录；过滤 `/buckets/.system/` |
| PUT 新对象 `a/b/c.txt` | 先新建目录 `a`、`b`，再新建文件 `c.txt` | 只取非目录条目 → 「新建」 |
| 覆盖 | 一条更新（旧、新条目同名，大小变化） | 「更新」，回读当前状态 |
| PUT `d/`（目录标记对象） | 新建**目录**条目 `d` | 被「忽略目录」规则一并忽略。FileAgent 不产生这种对象，可接受 |
| 分片上传（3 片） | `.uploads/<哈希_uploadId>/` 下的目录与分片新建（顺序不定）→ 完成时新建 `mp/`、新建 `mp/big.bin`（完整大小）→ 删除分片与上传目录 | 过滤 `/.uploads/`；只看到一条最终对象「新建」 |
| 中止的分片上传 | 全部发生在 `.uploads/` 内 | 全部过滤 |
| 服务端拷贝 | 新建目标对象 | 「新建」 |
| 删除对象 | 一条删除；空的父目录**不会**被删、也没有事件 | 「删除」 |
| 删除不存在的对象 | 无事件 | — |
| 删非空桶 | **409，无任何事件** | 与 D-037「由存储原子判空」一致 |
| 删空桶 | 删除目录 `/buckets/<桶>`（一条，`delete_chunks=false`）+ `.system/owners` 条目删除；其下残留的空目录不发事件 | 解释为「桶已删除」；按 D-037 第四条，若账本还有该桶的行即为事故 |

S3 接口不产生 rename；若有人经 filer HTTP / FUSE 重命名，事件里 `new_parent_path` 与 `dir` 不同，适配器按「删旧 + 建新」处理即可。
事件时间戳来自 filer 时钟（本机容器比宿主慢约 24ms），**不要拿它和其他来源的时间比较**——D-030 已规定 `observed_at` 取各自可信的时钟。

## 5. 对 spike（B3）的直接输入

- 适配器接口：`Subscribe(ctx, cursor) → 事件流 + 声明值`；持久化的只有**声明值**（和用于越界自检的最早日志位置），不持久化「最大已见时间戳」。
- 每条事件进索引前回读对象当前状态（S3 `HeadObject`），因此重放无害；事件只携带「哪个桶、哪个键、新建/更新/删除」。
- 断流重连：把（上次声明值，重连后首个心跳）标记为待核对窗口，交给对账；崩溃检测不靠水位。
- filer gRPC 连接配 mTLS（D-037 已知约束）；单 filer 部署订一条本地流即可，多 filer 时要逐个订各自的本地流（本次未测）。

## 6. 局限

- 单节点、本机 SSD、OrbStack；乱序幅度与心跳间隔是下界。
- 多 filer、mTLS、postgres2 等其他元数据库没有测。
- 声明值「无违例」的实测样本只有 55 次心跳；结论主要依据源码，实测是佐证。
